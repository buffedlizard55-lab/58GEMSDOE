Why the earlier portal error happened and why this file is safe

The portal error "Predicted values must be in range [0, 1]" is triggered by out-of-range or non-finite cells. This file uses the all-finite export policy: dots at exactly 1.0, zeros everywhere else including outside the scored footprint — nothing can violate [0,1] and no NaN exists. The fail-closed writer re-opens the written file and checks CRS, shape, transform, dtype, range, finiteness, zero-outside-footprint and zero-on-catalogue before the file is released (src/gems57/submission_writer.py).

What this submission is (method, one paragraph)

Candidate fault ridge axes are extracted from (a) the visible USGS/INGENIOUS catalogue skeleton and (b) the independent SGMC public fault compilation where it runs within the measured 8 px localization cap of the catalogue. On a hide-and-recover holdout (whole catalogue segments withheld per spatial block with buffered context), the across-strike distance between each candidate ridge and the nearest withheld segment was measured and an error scale sigma(block, type) fitted (~2.5-3.5 px). Per the lane, emission uses parallel dotted lines about ±sigma wide (spacing near the 3-px kernel radius), each dot at exactly 1.0, off the mapped catalogue. Holdout evidence: ribbon >> tight line (+0.201 pooled with an oracle accept test); the truth-free live rule itself was holdout-scored at 0.1309 (HOLDOUT-DTI).
