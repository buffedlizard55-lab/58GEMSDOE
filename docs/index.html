Why the earlier portal error cannot happen with this file

The portal rejects files with "Predicted values must be in range [0, 1]". That is caused by out-of-range or non-finite cells. This file is written by the fail-closed writer (src/gems57/submission_writer.py), which refuses to emit anything it has not re-opened and re-checked: dots at exactly 1.0, zeros everywhere else including outside the scored footprint, no NaN anywhere, no positive mass on the mapped catalogue, and CRS/shape/transform compared against the official sample_submission.tif.

Method (this session's lane)

  1. Feature stack. The official training_features.tif (19 GeoDAWN bands, 418,912,844 B, sha256 4371c82e…) is fetched from the owner's pinned git bridge and verified part-by-part and whole-file before use (scripts/fetch_feature_stack.sh, pins in data/bridge/feature_stack_pins.json).
  2. Operators. 16 NaN-aware local operators: structure-tensor coherence at σ=1 px and σ=3 px for RTP, TMI, isostatic gravity and detrended elevation; 3 px and 7 px local σ; Laplacian. All are NaN-aware because SciPy's recursive 1-D passes let a single nodata cell poison a whole line (regression-tested in tests/test_gems59.py).
  3. Ranking. HistGradientBoosting, positives = mapped catalogue, negatives sampled from the footprint, trained with one spatial quadrant held out (leave-one-quadrant-out) so a tested block never supplies training context.
  4. Emission. 3-px non-maximum suppression (the 300 m kernel radius) turns the probability field into a dotted line field; the field is truncated to a dot budget; dots are emitted at exactly 1.0.
  5. Budget. 36,394 dots, taken from the owner-raster record below, not from a guess. The holdout supplies the optimal dots-per-truth-pixel ratio ν*; the record supplies the absolute count.
